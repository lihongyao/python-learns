# 连接 `JOIN`

[表表达式与连接参考 ↪](https://www.postgresql.org/docs/18/queries-table-expressions.html)

`JOIN`把来自两个或多个表的行组合成一个结果集。连接条件通常比较两个表的键，但也可以使用任意布尔表达式；连接条件应明确写在`ON`或`USING`中，避免无意产生笛卡尔积。

本章介绍五种常用连接形式：

- `CROSS JOIN`：交叉连接，返回两侧行的笛卡尔积。
- `INNER JOIN`：内连接，只保留满足连接条件的组合；`JOIN`默认就是它。
- `LEFT OUTER JOIN`：左外连接，保留左表全部行。
- `RIGHT OUTER JOIN`：右外连接，保留右表全部行。
- `FULL OUTER JOIN`：全外连接，保留两侧未匹配的行。

接下来让我们创建两张表 **COMPANY** 和 **DEPARTMENT**。

**实例**

```postgresql

INSERT INTO company (id, name, age, address, salary)

	(4, 'Mark', 25, 'Rich-Mond ', 65000.00 ),
	(5, 'David', 27, 'Texas', 85000.00 ),
	(6, 'Kim', 22, 'South-Hall', 45000.00 ),
	(7, 'James', 24, 'Houston', 10000.00 ),
	(8, 'Paul', 24, 'Houston', 20000.00),
	(9, 'James', 44, 'Norway', 5000.00),
	(10, 'James', 45, 'Texas', 5000.00);
```

此时，COMPANY 表的记录如下：

```postgresql
INSERT INTO department (id, dept, emp_id)

```

## 交叉查询 `CROSS JOIN`

交叉连接返回两个表的笛卡尔积，即左表的每一行与右表的每一行组合。若两侧分别有`m`和`n`行，结果最多有`m × n`行；空表会使结果为空。它适合生成组合或日历等场景，连接大表前应确认结果规模。

语法格式：

```postgresql
SELECT ... FROM table1 CROSS JOIN table2 ...
```
假设有表 colors（颜色）和 sizes（尺寸）：

```postgresql
CREATE TABLE colors (
	id SERIAL PRIMARY KEY,
  color TEXT NOT NULL
);

CREATE TABLE sizes(
	id SERIAL PRIMARY KEY,
  size TEXT NOT NULL
);

INSERT INTO colors (color)
VALUES
	('红'),
	('蓝');
	
	
INSERT INTO sizes (size)
VALUES
	('S'),
	('M'),
	('L');
```

交叉查询：

```postgresql
SELECT color, size 
FROM colors 
CROSS JOIN sizes 
ORDER BY color;
```

结果示例：

```
 color | size 
-------+------
 红    | S
 红    | M
 红    | L
 蓝    | S
 蓝    | M
 蓝    | L
(6 行记录)
```

## 内连接 `INNER JOIN`

内连接只返回满足`ON`或`USING`条件的组合，任一侧没有匹配的行都会被过滤掉。省略`INNER`时，`JOIN`的默认语义就是内连接。

语法格式：

```postgresql
SELECT table1.column1, table2.column2...
FROM table1
[INNER] JOIN table2
ON table1.common_filed = table2.common_field;
```

基于上面的表，我们可以写一个内连接，在 department 表中根据 emp_id 关联查询 company 表中的员工姓名，输出员工姓名及其所属部门， 如下所示：

```postgresql
SELECT c.name, d.dept 
FROM company c
JOIN department d
ON c.id = d.emp_id;
```

结果示例：

```postgresql
 name  |    dept     
-------+-------------
 Paul  | IT Billing
 Allen | Engineering
 James | Finance
(3 行记录)
```

## 左外连接 `LEFT OUTER JOIN`

左外连接返回左表全部行和右表的匹配行；没有匹配时，右表列填为`NULL`。若要筛选“左表存在但右表无关联”的行，应在连接后判断右表的非空键为`NULL`，不要把右表条件不加区分地写到`WHERE`中，否则可能把外连接退化为内连接。

语法格式：

```postgresql
SELECT ... 
FROM table1 
LEFT [OUTER] JOIN table2 
ON conditional_expression ...
```

实例：查询所有员工及其部门（包括无部门的员工）

```postgresql
SELECT e.name, d.dept 
FROM company e
LEFT JOIN department d ON e.id = d.emp_id;
-- 结果示例：
-- company 的所有员工都会保留；未关联部门的行中 d.dept 为 NULL
```

## 右外连接 `RIGHT OUTER JOIN`

右外连接与左外连接对称，保留右表全部行。实际代码中通常通过交换左右表改写为左外连接，以便统一阅读方向。

语法格式：

```postgresql
SELECT ... 
FROM table1 
RIGHT [OUTER] JOIN table2 
ON conditional_expression ...
```

实例：查询所有部门及其员工（包括无员工的部门）

```postgresql
SELECT e.name, d.dept 
FROM company e
RIGHT JOIN department d ON e.id = d.emp_id;
-- 结果示例：
-- department 的所有部门都会保留；未关联员工的行中 e.name 为 NULL
```

## 全外连接 `FULL OUTER JOIN`

全外连接同时保留两侧所有行；无法匹配的一侧用`NULL`补齐，适合对账和差异比对。

语法格式：

```postgresql
SELECT ... 
FROM table1 
FULL [OUTER] JOIN table2 
ON conditional_expression ...
```

实例：合并员工和部门信息（保留所有记录）

```postgresql
SELECT e.name, d.dept 
FROM company e
FULL JOIN department d ON e.id = d.emp_id;
-- 结果示例：
-- 两侧未匹配的行都会保留，对应另一侧的列以 NULL 填充
```

# 操作符 `UNION`

## 概述

[组合查询参考 ↪](https://www.postgresql.org/docs/18/queries-union.html)

`UNION`、`UNION ALL`、`INTERSECT`和`EXCEPT`用于组合多个兼容的`SELECT`结果。`UNION`默认去除重复行，`UNION ALL`保留重复行；`INTERSECT`取交集，`EXCEPT`取左侧有而右侧没有的行。

**核心规则**：

- 每个`SELECT`的输出列数必须相同。
- 对应位置的数据类型必须能够通过类型解析规则转换为兼容类型；必要时应显式转换，避免类型推断结果不符合预期。
- 除非各分支单独用括号限制，最终的`ORDER BY`应放在整个组合查询末尾；组合查询不会保证结果顺序。

**基础语法**：

```postgresql
SELECT column1 [, column2 ]
FROM table1 [, table2 ]
[WHERE condition]

UNION

SELECT column1 [, column2 ]
FROM table1 [, table2 ]
[WHERE condition]
```

## 创建测试表与数据

**表1：`employees`（正式员工）**

```postgresql
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    department VARCHAR(20)
);

INSERT INTO employees (id, name, department) 
VALUES 
    (1, '张三', '技术部'),
    (2, '李四', '人事部'),
    (3, '王五', '财务部');
```

**表2：`contractors`（外包员工）**

```postgresql
CREATE TABLE contractors (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    department VARCHAR(20)
);

INSERT INTO contractors (id, name, department) 
VALUES 
    (4, '赵六', '技术部'),
    (5, '李四', '人事部'),  -- 重复姓名
    (6, '钱七', '市场部');
```

## 实例演示

#### 基本 UNION（去重）

合并所有员工姓名和部门，自动去除重复行（如“李四”仅出现一次）：

```postgresql
SELECT name, department FROM employees
UNION
SELECT name, department FROM contractors;
```

结果示例：

```postgresql
 name | department 
------+------------
 赵六 | 技术部
 钱七 | 市场部
 张三 | 技术部
 李四 | 人事部
 王五 | 财务部
(5 行记录)
```

#### UNION ALL（保留重复）

保留所有记录，包括重复的“李四”：

```postgresql
SELECT name, department FROM employees
UNION ALL
SELECT name, department FROM contractors;
```

结果示例：

```postgresql
 name | department 
------+------------
 张三 | 技术部
 李四 | 人事部
 王五 | 财务部
 赵六 | 技术部
 李四 | 人事部
 钱七 | 市场部
(6 行记录)
```

#### 多表合并与排序

合并三张表（假设新增 `interns` 表）并按姓名排序：

```postgresql
SELECT name, department FROM employees
UNION ALL
SELECT name, department FROM contractors
UNION ALL
SELECT name, department FROM interns
ORDER BY name;  -- 排序必须放在最后
```

## 常见应用场景

1. **数据整合**：合并结构相同的表（如按时间分表存储的历史数据）。
2. **汇总统计**：先组合多表数据，再用聚合函数计算总和或平均值。
3. **数据比对**：使用`EXCEPT`或`INTERSECT`查找差异或共同记录。

# NULL

[空值与三值逻辑参考 ↪](https://www.postgresql.org/docs/18/functions-comparison.html)

`NULL`表示缺失、未知或不适用的值，不等同于`0`、空字符串或`FALSE`。除非列声明了`NOT NULL`，否则列默认允许存储`NULL`。

**语法格式**：

当创建表时，NULL 的基本语法如下：

```postgresql
CREATE TABLE company(
   id INT PRIMARY KEY     NOT NULL,
   name           TEXT    NOT NULL,
   age            INT     NOT NULL,
   address        TEXT,
   salary         REAL
);
```

这里，`NOT NULL`表示该列必须包含非空值；插入或更新时，如果没有提供值且没有可用默认值，操作会失败。

允许`NULL`的列可以在插入时省略，或显式写入`NULL`。

在查询中，`NULL`参与普通比较会产生未知结果（`NULL`），而不是`TRUE`或`FALSE`；`WHERE`只保留结果为`TRUE`的行。因此，判断空值必须使用`IS NULL`或`IS NOT NULL`，也可以使用`IS DISTINCT FROM`进行空值安全比较。

`NULL`与`0`是不同概念，不能通过普通等号判断两者关系；聚合函数通常忽略输入中的`NULL`，但`COUNT(*)`会统计所有行。

**实例**

创建 COMPANY 表，数据内容如下：

```postgresql
INSERT INTO company (id, name, age, address, salary)
VALUES
	(1, 'Paul', 32, 'California', 20000.00 ),
	(2, 'Allen', 25, 'Texas', 15000.00 ),
	(3, 'Teddy', 23, 'Norway', 20000.00 ),
	(4, 'Mark', 25, 'Rich-Mond ', 65000.00 ),
	(5, 'David', 27, 'Texas', 85000.00 ),
	(6, 'Kim', 22, 'South-Hall', 45000.00 ),
	(7, 'James', 24, 'Houston', 10000.00 );
	
SELECT * FROM company;
 id | name  | age |  address   | salary 
----+-------+-----+------------+--------
  1 | Paul  |  32 | California |  20000
  2 | Allen |  25 | Texas      |  15000
  3 | Teddy |  23 | Norway     |  20000
  4 | Mark  |  25 | Rich-Mond  |  65000
  5 | David |  27 | Texas      |  85000
  6 | Kim   |  22 | South-Hall |  45000
  7 | James |  24 | Houston    |  10000
(7 行记录)
```

接下来我们用 UPDATE 语句把几个可设置为空的字段设置为 NULL ：

```postgresql

```

现在 COMPANY 表长这样：

```postgresql

----+-------+-----+------------+--------
```

**IS NOT NULL**

IS NULL 用来查找为 NULL 值的字段。下面是 IS NULL 操作符的用法，列出 SALARY（薪资） 值为空的记录：


# 别名

[列与表别名参考 ↪](https://www.postgresql.org/docs/18/queries-select-lists.html)

别名使用`AS`或直接写在对象名后，为查询结果中的列或`FROM`中的表指定临时名称。别名只在当前查询中有效，不会修改数据库对象的真实名称；表别名定义后，通常应使用别名引用该表。

**语法格式**：

```postgresql
-- 表的别名语法
SELECT column1, column2....
FROM table_name AS alias_name
WHERE [condition];

-- 列的别名语法:
SELECT column_name AS alias_name
FROM table_name
WHERE [condition];
```

# 触发器

[触发器参考 ↪](https://www.postgresql.org/docs/18/trigger-definition.html)

触发器是在指定事件发生时由 PostgreSQL 自动调用的函数。常见事件包括`INSERT`、`UPDATE`、`DELETE`和`TRUNCATE`，触发时机可以是`BEFORE`、`AFTER`或`INSTEAD OF`；还可以按每行（`FOR EACH ROW`）或每条语句（`FOR EACH STATEMENT`）触发。

触发器适合实现审计、派生字段维护和跨表校验，但会把隐式副作用加入写操作，增加排错和迁移复杂度。创建前应明确触发顺序、递归风险、异常处理和性能影响，并优先使用约束表达可声明的数据规则。

# 索引

[索引介绍 ↪](https://www.postgresql.org/docs/18/indexes.html)
[CREATE INDEX 参考 ↪](https://www.postgresql.org/docs/18/sql-createindex.html)

索引是独立维护的数据结构，用于帮助 PostgreSQL 更快定位表中的行，也可以支持排序、唯一性检查和部分约束。它不是表数据的副本；查询是否使用索引由规划器根据成本估算决定。

可以把索引理解为字典的检索目录：通过合适的键快速缩小查找范围，但目录本身也需要存储空间和维护成本。

索引可能加快选择、连接、排序或范围查询，但会增加磁盘占用，并使`INSERT`、`UPDATE`、`DELETE`产生额外维护开销。创建或删除索引不会改变表中的逻辑数据，但在生产环境要评估锁和构建时间。

使用`CREATE INDEX`可以指定索引名、目标表、一个或多个列/表达式以及排序方式。默认索引类型是`B-tree`；还可根据数据和查询选择`Hash`、`GiST`、`SP-GiST`、`GIN`或`BRIN`等类型。

唯一索引可阻止重复键，但表达业务唯一性时通常优先使用`UNIQUE`约束或主键，让约束清晰表达数据规则；PostgreSQL 会为它们自动创建所需的唯一索引。

## CREATE INDEX

CREATE INDEX （创建索引）的语法如下：

```postgresql
CREATE INDEX index_name ON table_name;
```

## 索引类型

### 单列索引

单列索引是一个只基于表的一个列上创建的索引，基本语法如下：

```postgresql
CREATE INDEX index_name
ON table_name (column_name);
```

### 组合索引

组合索引是基于表的多列上创建的索引，基本语法如下：

```postgresql
CREATE INDEX index_name
ON table_name (column1_name, column2_name);
```

单列还是组合索引，应由实际查询条件、列选择性、排序和连接方式决定，而不是简单按列数选择。组合索引遵循最左列优先的访问特性，创建前应查看代表性查询的`EXPLAIN`计划。

### 唯一索引

唯一索引同时提供查询优化和唯一性检查；默认情况下多个`NULL`通常不互相冲突，若业务要求把`NULL`也视为重复，应在 PostgreSQL 15+ 使用相应的`NULLS NOT DISTINCT`选项或约束定义。

```postgresql
CREATE UNIQUE INDEX index_name
on table_name (column_name);
```

### 局部索引

部分索引是在表的子集上构建的索引，子集由谓词定义，只有满足谓词的行会进入索引。查询条件必须能被规划器证明与该谓词匹配，索引才可能被使用。

```postgresql
CREATE INDEX index_name
ON table_name(column_list)
WHERE condition;
```

其中，`index_name`是索引名称，`table_name`是目标表，`column_list`是索引列或表达式，`condition`是决定哪些行进入索引的布尔谓词。

### 隐式索引

主键和唯一约束会自动创建唯一索引（除非复用已有适配索引）。外键约束不会自动为引用列创建索引；是否创建应根据被引用表更新、子表连接和删除操作的负载单独评估。

## 实例

下面实例将在 COMPANY 表的 SALARY 列上创建索引：

一个索引可以使用 PostgreSQL 的 DROP 命令删除。

```postgresql

```

您可以使用下面的语句来删除之前创建的索引：

```postgresql

```


## 什么情况下要避免使用索引？

是否需要索引没有适用于所有表的固定规则。小表、低选择性列或写入远多于读取的表，新增索引可能收益很小；但含有较多`NULL`并不自动意味着不应建索引，实际效果取决于查询谓词、索引类型和数据分布。

使用索引时，应结合代表性负载和`EXPLAIN (ANALYZE, BUFFERS)`评估：

- 索引列应服务于真实的过滤、连接、排序或唯一性需求。
- 写入密集型表要控制索引数量和宽度，避免维护成本超过查询收益。
- 定期清理未使用或重复索引，并关注索引膨胀和统计信息是否新鲜。
- 大表在线创建索引时可评估`CREATE INDEX CONCURRENTLY`；它不能放在事务块中，但能减少对并发写入的阻塞。

# TRANSACTION

[事务与并发控制参考 ↪](https://www.postgresql.org/docs/18/tutorial-transactions.html)
[事务隔离参考 ↪](https://www.postgresql.org/docs/18/transaction-iso.html)

事务是数据库执行工作的基本边界，由一条或多条语句组成。事务将相关修改作为一个整体提交或回滚，并通过隔离级别和锁协调并发访问。

1. **原子性**：事务内的语句全部成功才提交；出错时可以回滚未提交的修改。
2. **一致性与隔离性**：约束维护数据规则，MVCC和锁决定并发事务能看到什么以及如何相互等待。
3. **持久性**：提交成功后，已提交结果会按 WAL 和相关持久性配置处理。

## 事务的 ACID 属性

| 属性                     | PostgreSQL 实现机制                                          | 实际场景示例                                                 |
| :----------------------- | :----------------------------------------------------------- | ------------------------------------------------------------ |
| **原子性** (Atomicity)   | 事务内操作要么全部提交，要么全部回滚；保存点还可以支持局部回滚。 | 转账事务：扣款和到账操作必须同时成功，否则撤销未提交修改。   |
| **一致性** (Consistency) | 约束、触发器和应用规则共同维护数据有效性；数据库只保证其能够检查到的规则。 | 账户余额不允许为负值，违反约束的语句会失败。         |
| **隔离性** (Isolation)   | 默认是`READ COMMITTED`；每条语句读取自己的快照，避免脏读，但可能出现不可重复读。 | 事务A两次查询之间，事务B提交的修改可能被A第二次查询看到。 |
| **持久性** (Durability)  | 提交是否能在崩溃后保留，取决于 WAL、同步提交和存储系统等配置。 | `COMMIT`成功后，数据库会按持久性配置处理已提交记录。 |

## 事务控制命令

### 1. 开始事务

```postgresql
BEGIN;  -- 或 BEGIN TRANSACTION;
```

- **作用**：显式开启事务，后续操作在提交前对其他会话不可见（隔离级别和对象类型会影响细节）。
- **注意**：PostgreSQL的大多数 DDL 可以放在事务中并回滚；少数命令（例如`CREATE INDEX CONCURRENTLY`、`VACUUM`）不能在事务块内执行。

### 2. 提交事务

```postgresql
COMMIT;  -- 或 COMMIT AND CHAIN（提交后立即启动新事务，减少网络往返）
```

- **效果**：确认事务中的变更并释放该事务持有的锁；持久化时序受同步提交等配置影响。

### 3. 回滚事务

```postgresql
ROLLBACK;  -- 或 ROLLBACK TO SAVEPOINT（部分回滚到保存点）
```

- **场景**：事务执行出错时撤销全部未提交操作，或通过保存点（`SAVEPOINT`）实现局部回滚。

## 实战示例与优化技巧

1. **基础事务流程**

   ```postgresql
   BEGIN;
   UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;  -- 扣款  
   UPDATE accounts SET balance = balance + 100 WHERE user_id = 2;  -- 到账  
   COMMIT;  -- 若任一UPDATE失败，自动回滚
   ```

2. **事务设计与性能**

   - **控制事务范围**：事务应覆盖一个完整业务动作；过大的事务会增加锁持有时间、WAL和回滚成本，盲目拆分又可能破坏原子性。
   - **链式事务**：`COMMIT AND CHAIN`会在提交后立即开启同隔离级别的新事务，适合确实需要连续事务的客户端循环；它不是通用的性能开关。
   - **WAL 参数**：`commit_delay`、`commit_siblings`等参数应在压测和监控基础上调整，不应把参数修改当作默认优化步骤。

3. **并发控制**

   - **隔离级别选择**：

      - **Read Committed**（默认）：每条语句使用自己的快照；避免脏读，但同一事务中两次查询可能看到不同已提交结果。
      - **Repeatable Read**：事务使用稳定快照，避免脏读和不可重复读；遇到并发更新冲突时，事务可能需要重试。
      - **Serializable**：提供最强隔离，可能因序列化失败需要重试，吞吐量和冲突成本要通过压测评估。

   - **锁机制**：

     ```postgresql
      SELECT * FROM orders WHERE id = 100 FOR UPDATE;  -- 锁定选中的行，防止并发事务修改
     ```

## 常见问题与解决方案

- **死锁**：PostgreSQL会检测死锁并中止其中一个事务；应用应按固定顺序访问资源，并准备重试被中止的事务。
- **长事务阻塞**：监控`pg_stat_activity`、锁等待和事务年龄，定位后再取消或终止会话；不要只依赖强制终止。
- **事务中止状态**：事务内某条语句失败后，后续语句通常会收到“current transaction is aborted”，应执行`ROLLBACK`或回滚到保存点。

# LOCK

[显式锁定参考 ↪](https://www.postgresql.org/docs/18/explicit-locking.html)

锁是 PostgreSQL 并发控制的一部分，用于协调表、行、事务和其他数据库对象的并发访问。MVCC让许多普通读写可以并行，但并不意味着所有读写都互不阻塞。

1. **并发协调**：不同锁模式之间按冲突矩阵等待或并行；`SELECT ... FOR UPDATE`等锁定子句会锁住选中的行。
2. **数据完整性**：锁和约束共同防止不兼容的并发修改；应用仍需设计好更新顺序和冲突重试。
3. **排查阻塞**：可以结合`pg_stat_activity`和`pg_locks`查看等待会话、锁类型和阻塞关系。

显式表锁应尽量缩小范围和持有时间；`LOCK TABLE`会按指定模式锁定整张表，生产环境使用前应确认对并发读写的影响。

# 常用函数

[函数与操作符参考 ↪](https://www.postgresql.org/docs/18/functions.html)

PostgreSQL 提供日期/时间、字符串、数学、聚合、JSON、数组和系统信息等函数。函数的参数类型、返回类型、是否忽略`NULL`以及是否具有副作用都应以官方文档为准；同名函数可能因参数类型不同而重载。

编写查询时，优先选择语义明确且能利用索引的表达式；对列套用函数可能影响普通索引的使用，必要时可评估表达式索引。生产代码还应明确时区、数值精度、`NULL`处理和函数的稳定性属性。
