# 模式

[模式参考 ↪](https://www.postgresql.org/docs/18/ddl-schemas.html)

PostgreSQL 的`模式（schema）`是数据库中的命名空间。模式可以包含表、视图、序列、索引、数据类型、函数和操作符等对象。

一个数据库可以有多个模式，同一个数据库中不同模式可以拥有同名对象：

```text
数据库 app_db
├── 模式 app
│   └── 表 app.users
├── 模式 audit
│   └── 表 audit.events
└── 模式 public
    └── 表 public.products
```

模式和数据库、角色的作用范围不同：

- 数据库属于数据库集群；连接时一次只能进入一个数据库。
- 模式属于某一个数据库；不同数据库可以有同名模式。
- 角色在整个数据库集群中有效；角色可以拥有或访问多个数据库中的模式。
- 模式不能嵌套，但可以使用点号限定对象名称，例如`app.users`。

使用模式的主要目的：

- 将业务、审计、扩展或第三方应用的对象分组。
- 避免不同模块之间的对象名称冲突。
- 在同一个数据库中为不同角色划分对象边界。
- 配合权限和搜索路径，控制对象的访问方式。

# 创建模式

## 基本语法

创建模式需要当前数据库的`CREATE`权限；超级用户可以绕过权限检查：

```postgresql
CREATE SCHEMA app;
```

如果希望模式由专门的所有者角色管理，可以指定`AUTHORIZATION`：

```postgresql
CREATE SCHEMA app AUTHORIZATION app_owner;
```

`app_owner`可以是第 03 章中介绍的`NOLOGIN`所有者角色。指定其他角色作为所有者时，执行者必须能够通过`SET ROLE`切换为该角色。

模式名称应使用小写字母、数字和下划线，长度遵守 PostgreSQL 标识符限制。以`pg_`开头的名称保留给系统使用，不能创建为普通用户模式。

## 避免重复创建

PostgreSQL 支持`CREATE SCHEMA IF NOT EXISTS`：

```postgresql
CREATE SCHEMA IF NOT EXISTS app;
```

如果模式已经存在，该命令会发出提示并跳过创建；它不会检查已有模式的所有者、权限或内容是否符合预期。部署脚本仍应单独检查这些属性。

> `CREATE SCHEMA IF NOT EXISTS`不能与同一条语句中的模式对象子命令一起使用。如果要同时创建表或视图，应先创建模式，再使用带模式限定的对象名称。

## 在模式中创建对象

使用`模式名.对象名`创建表、视图和其他对象：

```postgresql
CREATE TABLE app.users (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username text NOT NULL UNIQUE
);

CREATE VIEW app.active_users AS
SELECT id, username
FROM app.users;
```

限定名可以避免对象被错误地创建到当前搜索路径中的其他模式。它也能让迁移脚本更容易审查和重复执行。

[CREATE SCHEMA 参考 ↪](https://www.postgresql.org/docs/18/sql-createschema.html)

# 查看模式和对象

## 使用 psql 元命令

在`psql`中可以使用以下元命令：

```postgresql
\dn
\dn+
\dt app.*
\dv app.*
\df app.*
\d app.users
```

- `\dn`列出模式。
- `\dn+`显示模式所有者和权限。
- `\dt app.*`列出`app`模式中的表。
- `\dv app.*`列出视图；`\df app.*`列出函数。
- `\d app.users`查看指定表的列、索引和约束。

`psql`元命令不需要分号；SQL 查询和 DDL 语句通常需要分号。

## 查询系统目录

模式的元数据保存在`pg_namespace`中。可以查询模式名、所有者和系统标记：

```postgresql
SELECT
    nspname AS schema_name,
    pg_get_userbyid(nspowner) AS owner,
    nspacl AS access_privileges
FROM pg_namespace
ORDER BY nspname;
```

只查看用户创建的模式：

```postgresql
SELECT
    nspname AS schema_name,
    pg_get_userbyid(nspowner) AS owner
FROM pg_namespace
WHERE nspname NOT LIKE 'pg_%'
  AND nspname <> 'information_schema'
ORDER BY nspname;
```

`information_schema`和`pg_catalog`是系统提供的特殊模式。应用通常不应在其中创建对象，也不应随意修改其中的内容。

## 查看当前模式和搜索路径

```postgresql
SELECT current_schema();
SELECT current_schemas(true);
SHOW search_path;
```

`current_schema()`返回当前搜索路径中的第一个有效模式；`current_schemas(true)`返回解析后的模式列表，其中包含隐式搜索的系统模式。

# public 模式

每个新数据库通常都会有一个名为`public`的模式。没有写模式限定名时，表等对象默认会创建到搜索路径中的第一个可用模式，默认配置通常最终使用`public`：

```postgresql
CREATE TABLE public.products (
    id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL
);
```

`public`只是一个普通模式，并没有跨数据库或自动授予所有业务权限的特殊能力。新建数据库中通常允许所有角色使用它，但“能够查找对象”和“能够创建对象”是两种不同权限。

PostgreSQL 15 及更高版本的新集群通常不会再向`PUBLIC`授予`public`模式的`CREATE`权限；从旧版本升级的数据库可能保留旧权限，应显式检查：

```postgresql
SELECT
    has_schema_privilege(current_user, 'public', 'USAGE')  AS can_use,
    has_schema_privilege(current_user, 'public', 'CREATE') AS can_create;

REVOKE CREATE ON SCHEMA public FROM PUBLIC;
```

`PUBLIC`表示所有角色，包括以后创建的角色。撤销`CREATE`只会阻止在该模式中创建新对象，不会删除已有对象，也不会撤销`USAGE`。

如果业务对象使用独立的`app`模式，可以让`public`只保留必要的公共对象，并把应用对象全部写成`app.object_name`。

# 模式搜索路径

## 什么是 search_path

当 SQL 中使用未限定名称时，PostgreSQL 会按照`search_path`从左到右查找对象：

```postgresql
SET search_path TO app, public;
SELECT * FROM users;
```

上例中，PostgreSQL 会先查找`app.users`，找不到时再查找`public.users`。如果两个模式都有名为`users`的表，会使用搜索路径中最先匹配的对象。

创建未限定对象时，搜索路径中第一个存在的模式会作为默认目标；当前角色还必须拥有该模式的`CREATE`权限，否则创建会失败。因此，查询路径和创建目标都不应依赖不清晰的默认值。

默认搜索路径通常类似于：

```postgresql
SHOW search_path;
-- "$user", public
```

`$user`表示与当前角色同名的模式；如果该模式不存在，这一项会被忽略。`pg_catalog`即使没有写在`search_path`中，也会被隐式搜索。

## 设置会话搜索路径

只在当前连接中临时设置：

```postgresql
SET search_path TO app, pg_catalog;
```

也可以在连接时设置：

```shell
PGOPTIONS='-c search_path=app,pg_catalog' psql -d app_db
```

在应用角色和指定数据库上设置默认值：

```postgresql
ALTER ROLE app_user IN DATABASE app_db
    SET search_path TO app, pg_catalog;
```

`ALTER ROLE ... SET`只影响之后创建的新会话；已经存在的连接需要重新连接。连接池中如果长时间复用连接，应在连接初始化时确认`search_path`。

## search_path 的安全性

搜索路径中的模式如果允许不受信任的角色创建对象，就可能出现名称遮蔽：

- 攻击者可以在靠前的模式中创建与表、函数或类型同名的对象。
- 未限定的查询或函数调用可能解析到错误对象。
- 依赖未限定函数名的安全代码可能在意外的权限上下文中执行。

推荐的安全做法：

- 应用 SQL 尽量使用`app.table_name`这样的限定名。
- 让应用角色只有模式`USAGE`，不要给它不必要的`CREATE`。
- 搜索路径中只放受信任且权限边界清晰的模式。
- 在安全敏感的函数中显式设置安全搜索路径，并避免把可写模式放在其中。

例如，应用角色只访问`app`模式：

```postgresql
REVOKE CREATE ON SCHEMA app FROM PUBLIC;
GRANT USAGE ON SCHEMA app TO app_user;

ALTER ROLE app_user IN DATABASE app_db
    SET search_path TO app, pg_catalog;
```

[搜索路径与模式参考 ↪](https://www.postgresql.org/docs/18/ddl-schemas.html)

# 模式权限

## USAGE 与 CREATE

模式级权限最常用的是：

| 权限 | 含义 |
| :--- | :--- |
| `USAGE` | 允许查找和访问模式中的对象，但仍需对象本身的权限 |
| `CREATE` | 允许在模式中创建新对象；不等于可以修改或删除他人拥有的对象 |

授权模式权限：

```postgresql
GRANT USAGE ON SCHEMA app TO app_user;
GRANT CREATE ON SCHEMA app TO app_writer;
```

如果`app_user`需要读取表，还必须授予表级权限：

```postgresql
GRANT SELECT ON ALL TABLES IN SCHEMA app TO app_user;
GRANT USAGE, SELECT, UPDATE
    ON ALL SEQUENCES IN SCHEMA app TO app_user;
```

模式`USAGE`、表的`SELECT`和序列的`USAGE`是不同层次的权限，缺少任意一层都可能导致访问失败。对于身份列和`serial`列，序列权限是否需要取决于插入方式和访问对象；统一配置序列权限可以减少迁移脚本中的权限遗漏。

## 按角色规划所有者和访问者

推荐使用专门的所有者角色与登录角色分离：

```postgresql
-- app_owner：NOLOGIN，负责拥有模式和对象
-- app_user：LOGIN，只获得应用需要的访问权限

CREATE SCHEMA app AUTHORIZATION app_owner;

GRANT USAGE ON SCHEMA app TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE
    ON ALL TABLES IN SCHEMA app TO app_user;
GRANT USAGE, SELECT, UPDATE
    ON ALL SEQUENCES IN SCHEMA app TO app_user;
```

如果`app_user`还需要执行函数，应另外授予函数的`EXECUTE`权限；模式`USAGE`不会自动授予表、序列或函数权限。

## 默认权限

普通的`GRANT`只影响已经存在的对象。以后新建的表、序列和函数，需要使用`ALTER DEFAULT PRIVILEGES`预先设置：

```postgresql
ALTER DEFAULT PRIVILEGES
    FOR ROLE app_owner
    IN SCHEMA app
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;

ALTER DEFAULT PRIVILEGES
    FOR ROLE app_owner
    IN SCHEMA app
    GRANT USAGE, SELECT, UPDATE ON SEQUENCES TO app_user;
```

默认权限有三个容易混淆的边界：

- 它只影响之后创建的对象，不会追溯修改已有对象。
- 它针对“创建对象的角色”；如果`app_owner`通过成员关系让`app_user`创建对象，实际创建者仍是`app_user`，不会自动套用`app_owner`的默认权限。
- `IN SCHEMA app`只限定对象所在模式；它不改变模式本身的`USAGE`或`CREATE`权限。

检查默认权限可以使用：

```postgresql
\ddp
```

[权限参考 ↪](https://www.postgresql.org/docs/18/ddl-priv.html)
[ALTER DEFAULT PRIVILEGES 参考 ↪](https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html)

# 修改模式

只有模式所有者或超级用户可以修改模式。重命名模式时，还需要当前数据库的`CREATE`权限：

```postgresql
ALTER SCHEMA app RENAME TO core;
```

修改模式所有者时，执行者需要能够`SET ROLE`到新所有者，并且新所有者需要具有当前数据库的`CREATE`权限：

```postgresql
ALTER SCHEMA core OWNER TO app_owner;
```

重命名模式不会自动更新应用中的字符串、连接配置或未限定对象名称。迁移前应搜索代码、视图定义、函数定义和权限脚本中的旧模式名。

[ALTER SCHEMA 参考 ↪](https://www.postgresql.org/docs/18/sql-alterschema.html)

# 删除模式

## RESTRICT 与 CASCADE

删除空模式可以使用默认的`RESTRICT`行为：

```postgresql
DROP SCHEMA IF EXISTS app;
```

如果模式中还有对象，`RESTRICT`会拒绝删除。`CASCADE`会删除模式中的对象，以及依赖这些对象的其他对象：

```postgresql
DROP SCHEMA app CASCADE;
```

`CASCADE`不可逆地删除表、视图、函数、类型和相关依赖对象。生产环境执行前应先查看依赖关系、完成可验证的备份，并在维护窗口中操作。模式所有者即使不拥有其中某些对象，也可能删除整个模式，因此所有者角色必须严格控制。

删除前可以先查看模式中的主要对象：

```postgresql
SELECT schemaname, tablename
FROM pg_tables
WHERE schemaname = 'app'
ORDER BY tablename;

SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_schema = 'app'
ORDER BY table_name;
```

[DROP SCHEMA 参考 ↪](https://www.postgresql.org/docs/18/sql-dropschema.html)

# 设计模式

## 常见组织方式

| 模式 | 适用内容 | 注意事项 |
| :--- | :--- | :--- |
| `app` | 核心业务表、视图和函数 | 由所有者角色维护，应用角色按需访问 |
| `audit` | 审计日志和变更记录 | 通常只允许写入服务或审计角色 |
| `reporting` | 报表视图和物化视图 | 避免直接向报表用户开放业务表 |
| 扩展专用模式 | 第三方扩展对象 | 依据扩展文档和升级流程管理 |
| `public` | 兼容旧应用或真正公共对象 | 不要默认放置所有业务对象 |

模式是命名空间和权限边界，不是租户隔离的完整方案。多租户系统还要结合行级安全策略、独立数据库或独立集群等设计；只创建一个模式并不能自动阻止跨租户访问。

## 推荐的部署顺序

一个较容易审查的初始化顺序如下：

1. 使用管理员或数据库所有者角色创建模式。
2. 确认模式所有者和数据库级`CREATE`权限。
3. 撤销不受信任角色在公共模式中的`CREATE`权限。
4. 为应用角色授予模式`USAGE`和所需对象权限。
5. 使用`ALTER DEFAULT PRIVILEGES`覆盖未来对象。
6. 迁移脚本使用模式限定名创建对象。
7. 使用最低权限的应用角色进行真实连接测试。

# 综合示例

下面的示例展示一个“对象所有者”和“应用访问者”分离的模式配置。假设`app_owner`和`app_user`已经在第 03 章中创建：

```postgresql
-- 由管理员执行
CREATE SCHEMA app AUTHORIZATION app_owner;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

GRANT USAGE ON SCHEMA app TO app_user;

-- 由 app_owner 执行，或由能够 SET ROLE 到 app_owner 的管理员执行
CREATE TABLE app.orders (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_no   text NOT NULL UNIQUE,
    created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    total      numeric(12, 2) NOT NULL CHECK (total >= 0)
);

GRANT SELECT, INSERT, UPDATE
    ON app.orders TO app_user;

GRANT USAGE, SELECT, UPDATE
    ON ALL SEQUENCES IN SCHEMA app TO app_user;

ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app
    GRANT SELECT, INSERT, UPDATE ON TABLES TO app_user;

ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app
    GRANT USAGE, SELECT, UPDATE ON SEQUENCES TO app_user;

ALTER ROLE app_user IN DATABASE app_db
    SET search_path TO app, pg_catalog;
```

> 如果需要按最小权限单独授权身份列或`serial`列使用的序列，序列对象名属于实现细节，迁移脚本不应盲目假定它一定叫`orders_id_seq`。先用`\d app.orders`或系统目录确认实际序列名；一般情况下，使用`ON ALL SEQUENCES IN SCHEMA app`更适合批量迁移。

# 常见问题

## schema "xxx" already exists

模式已经存在。使用`\dn`或`pg_namespace`确认其所有者和权限；`CREATE SCHEMA IF NOT EXISTS`只会跳过创建，不会修正已有模式。

## no schema has been selected to create in

当前`search_path`中没有存在的模式可作为未限定对象的默认目标，或者搜索路径被设置为空。检查：

```postgresql
SHOW search_path;
SELECT current_schema();
SELECT has_schema_privilege(current_user, 'app', 'CREATE');
```

如果第一个存在的模式缺少`CREATE`权限，通常会收到`permission denied for schema`，应按下一节检查权限。修复搜索路径或为正确的模式授予`CREATE`，但不要为了消除错误而给`PUBLIC`授予过宽权限。

## permission denied for schema app

通常缺少`USAGE`，或者操作需要在模式中创建对象但缺少`CREATE`：

```postgresql
GRANT USAGE ON SCHEMA app TO app_user;
GRANT CREATE ON SCHEMA app TO app_writer;
```

即使有模式`USAGE`，也仍需检查表、序列、函数本身的权限。

## relation "users" does not exist

可能原因包括：

- 当前连接到了错误的数据库。
- 表实际位于其他模式。
- `search_path`没有包含目标模式。
- 对象名使用了大小写敏感的双引号，查询时写法不一致。

先用限定名确认：

```postgresql
SELECT * FROM app.users;
SHOW search_path;
\dt *.*
```

## relation "app.users" does not exist

确认当前连接的数据库中确实存在`app.users`，并检查模式名称和表名称是否拼写正确。模式不能跨数据库访问；如果对象在另一个数据库，必须重新连接到那个数据库。

## cannot drop schema because other objects depend on it

默认的`RESTRICT`阻止删除仍有对象或依赖关系的模式。先清点对象和依赖，再决定是逐个迁移/删除，还是在确认影响后使用`CASCADE`。不要把`CASCADE`当作常规清理命令。

## 函数调用到了错误的对象

检查`search_path`和函数参数类型。未限定函数名可能解析到搜索路径靠前模式中的对象；安全敏感操作应使用受信任模式、限定名称或显式设置搜索路径。

# 操作检查清单

- 模式按业务边界、审计、报表或扩展用途划分，不要为每张表机械创建一个模式。
- 模式、数据库和角色的作用范围要分清；模式不能替代多租户隔离。
- 新建模式时明确所有者，优先使用`NOLOGIN`所有者角色。
- 应用 SQL 优先使用模式限定名，并为连接设置受控的`search_path`。
- 模式`USAGE`、模式`CREATE`、表权限和序列权限分别配置。
- 检查 PostgreSQL 15+ 新集群与旧版本升级数据库的`public`权限差异。
- 使用`ALTER DEFAULT PRIVILEGES`覆盖未来对象，但不要误以为它会修改已有对象。
- 删除模式前检查对象、依赖和备份；`CASCADE`必须经过明确审批。
- 迁移和排错时确认数据库、模式、对象所有者及`search_path`。

# 小结

模式是数据库中的命名空间，也是组织对象和划分权限的重要边界。本章介绍了模式的创建、查看、搜索路径、`public`模式、`USAGE`/`CREATE`权限、默认权限、修改、删除和常见排错。掌握模式后，创建表和编写查询时应优先使用清晰的模式限定名，并让应用角色只获得必要的访问权限。
