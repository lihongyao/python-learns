# 数据类型

[数据类型参考 ↪](https://www.postgresql.org/docs/18/datatype.html)

数据类型决定一列可以保存什么值、如何存储、能够使用哪些运算符，以及输入数据不符合规则时如何报错。选择类型时，先问“这个字段在业务上代表什么”，再考虑空间和性能；不要因为某个类型名字看起来更短就盲目使用它。

可以把常见对象的类型选择先记成下面这张速查表：

| 业务含义 | 通常的选择 | 说明 |
| :--- | :--- | :--- |
| 普通整数 | `integer` | 范围和空间较均衡 |
| 可能超过 21 亿的整数 | `bigint` | 适合大型表的编号、计数器 |
| 金额、精确比例 | `numeric(p, s)` | 精确计算，不使用浮点数表示金额 |
| 科学计算、允许近似值 | `double precision` | 范围大、速度快，但存在舍入误差 |
| 普通文本 | `text` | 不需要人为设置长度上限 |
| 有明确长度规则的文本 | `varchar(n)` 或 `text + CHECK` | 长度约束是业务规则时再声明 |
| 日历日期 | `date` | 不需要时分秒 |
| 跨时区的时间点 | `timestamptz` | 保存一个明确的时间点 |
| 本地日程或“墙上时间” | `timestamp` | 不代表全球唯一的时间点 |
| 开关状态 | `boolean` | `TRUE`、`FALSE` 或 `NULL` |
| 分布式唯一标识 | `uuid` | PostgreSQL 18 可生成 UUID v4/v7 |
| 结构灵活的属性 | `jsonb` | 需要查询或建立索引时优先考虑 |
| 小量、原子性的标签集合 | 数组，如 `text[]` | 复杂关系不要用数组代替关联表 |

# 类型与约束

类型和约束解决的是不同问题：

- 类型回答“值是什么”，例如整数、金额、时间点或 JSON。
- `NOT NULL` 回答“值是否必须存在”。
- `CHECK` 回答“值是否满足业务条件”。
- `UNIQUE` 和主键回答“值是否必须唯一”。
- 外键回答“值是否必须引用另一张表中的记录”。

例如，`numeric(12,2)` 只约束数值精度和小数位；它不会自动保证金额非负，也不会自动保证每笔金额唯一：

```postgresql
CREATE TABLE invoice_items (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    amount      numeric(12, 2) NOT NULL CHECK (amount >= 0),
    description text
);
```

同一个基础类型可以搭配不同约束，形成不同的业务语义。后续章节介绍表结构时，应把类型、默认值和约束一起设计。

# 数值类型

## 整数类型

| 类型 | 存储空间 | 取值范围 | 常见用途 |
| :--- | :---: | :--- | :--- |
| `smallint` / `int2` | 2 字节 | -32768 到 32767 | 确实范围很小的状态或计数 |
| `integer` / `int` / `int4` | 4 字节 | -2147483648 到 2147483647 | 默认的整数选择 |
| `bigint` / `int8` | 8 字节 | -9223372036854775808 到 9223372036854775807 | 大规模编号、金额的最小单位、累计计数 |

`integer` 通常是空间、范围和性能之间最均衡的选择。只有在范围确实很小并且数据量巨大时才考虑 `smallint`；如果编号或计数未来可能超过 21 亿，应从一开始使用 `bigint`。

整数超出范围时会报错，而不是自动变成更大的类型：

```postgresql
SELECT 2147483647::integer;  -- 成功
SELECT 2147483648::integer;  -- ERROR: integer out of range
```

不同整数类型混合运算时，结果类型由 PostgreSQL 的类型转换规则决定。对边界值和大数计算，建议显式转换为目标类型。

## 精确小数

`numeric` 和 `decimal` 是同一个类型的两个名称，用于需要精确结果的计算。声明形式为：

```text
NUMERIC(precision, scale)
```

- `precision` 是总有效数字位数，包含小数点两侧的数字。
- `scale` 是小数点右侧保留的位数。
- 当输入的小数位多于 `scale` 时，PostgreSQL 会按目标小数位进行四舍五入。
- 整数部分超过 `precision - scale` 时会报错。

金额字段可以这样设计：

```postgresql
CREATE TABLE payments (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    amount     numeric(12, 2) NOT NULL CHECK (amount >= 0),
    currency   char(3) NOT NULL
);

INSERT INTO payments (amount, currency)
VALUES (199.995, 'CNY');

SELECT amount FROM payments;
-- numeric(12,2) 会保存为 200.00
```

`numeric` 的计算通常比整数和浮点数慢，但它能避免二进制浮点误差。金额、税率、汇率和需要可复核的小数结果，优先使用 `numeric`。

> `money` 类型受数据库的 `lc_monetary` 区域设置影响，输入输出格式和小数精度可能因环境不同而变化。跨环境迁移或多币种系统通常使用 `numeric` 加独立的货币代码列，而不是 `money`。

## 浮点类型

- `real`：4 字节，至少约 6 位十进制有效数字。
- `double precision`：8 字节，至少约 15 位十进制有效数字。

这两种类型保存的是近似值，适合测量值、统计模型和科学计算，不适合金额或需要严格相等比较的值：

```postgresql
SELECT 0.1::double precision + 0.2::double precision;
-- 结果可能显示为 0.30000000000000004

SELECT 0.1::numeric + 0.2::numeric;
-- 结果为 0.3
```

浮点数比较应设置可接受误差，或使用 `numeric`：

```postgresql
-- 不建议直接依赖浮点数相等
SELECT measured_value
FROM sensor_readings
WHERE abs(measured_value - 0.3) < 0.000001;
```

`real` 和 `double precision` 还支持 `Infinity`、`-Infinity` 和 `NaN` 等特殊值。除非业务明确需要，否则不要让这些值进入普通指标或金额字段。

## 自增列：身份列与 serial

### 推荐使用身份列

PostgreSQL 10 及更高版本支持 SQL 标准身份列。它由 PostgreSQL 管理关联序列，推荐用于新表的自增主键：

```postgresql
CREATE TABLE users (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username   text NOT NULL UNIQUE
);
```

`GENERATED ALWAYS` 表示通常不允许插入方自行提供编号。如果确实需要导入指定编号，可以使用 `OVERRIDING SYSTEM VALUE`。如果希望“未提供时自动生成、提供时也允许显式值”，可改用：

```postgresql
CREATE TABLE imported_rows (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payload jsonb NOT NULL
);
```

### serial 是历史写法

`serial`、`bigserial` 和 `smallserial` 不是真正的数据类型，而是创建整数列、序列和默认值的一种简写：

```postgresql
CREATE TABLE legacy_events (
    id      bigserial PRIMARY KEY,
    payload text
);
```

新项目优先使用身份列；维护旧项目时仍会经常看到 `serial`。无论身份列还是 `serial`，序列都不是“无间隙编号器”：

- 事务回滚后，已经取出的序列值不会自动归还。
- 多个会话并发取值时，编号顺序不一定等于提交顺序。
- 删除数据不会重新使用旧编号。

因此，自增列适合作为技术主键，不应直接当作业务订单号或连续发票号。

[数值类型参考 ↪](https://www.postgresql.org/docs/18/datatype-numeric.html)

# 字符串与二进制

## text、varchar 与 char

| 类型 | 行为 | 建议 |
| :--- | :--- | :--- |
| `text` | 变长文本，不需要声明长度 | 普通文本的默认选择 |
| `varchar(n)` | 最多 `n` 个字符 | 确实存在长度上限时使用 |
| `varchar` | 变长文本，不限制长度 | 可用，但通常直接写 `text` 更清晰 |
| `char(n)` | 定长、右侧补空格 | 只有协议明确要求定长时使用 |

`varchar(n)` 和 `char(n)` 的长度单位是字符，不是字节。多字节字符集下，一个汉字可能占用多个字节，但仍只计一个字符。

`char(n)` 会用空格补齐，比较时尾随空格通常没有语义；`text` 和 `varchar` 的尾随空格有语义，使用 `LIKE` 或正则表达式时尤其要注意。PostgreSQL 中 `char(n)` 没有传统数据库里常见的性能优势，通常不应为了“定长更快”而使用它。

例如，用户名的业务规则可以写成约束，而不必把任意长度都猜成 255：

```postgresql
CREATE TABLE accounts (
    username text NOT NULL
        CHECK (char_length(username) BETWEEN 3 AND 32),
    display_name text
);
```

长度约束、字符类型和编码是三件不同的事：

- `char_length(value)` 统计字符数。
- `octet_length(value)` 统计字节数。
- 数据库编码决定哪些字符可以存储。

如果要保存普通文本，优先使用 `text`；如果接口契约明确规定最大字符数，再使用 `varchar(n)` 或 `CHECK`。

## 二进制数据：bytea

`bytea` 用于保存原始字节，例如加密后的数据、压缩内容或小型文件。它和文本不同，可以保存值为零的字节：

```postgresql
CREATE TABLE attachments (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    content bytea NOT NULL
);

INSERT INTO attachments (content)
VALUES (decode('89504E47', 'hex'));
```

应用层通常通过驱动程序的二进制参数写入 `bytea`，不需要手工拼接十六进制字符串。较大的图片、视频和备份文件通常更适合对象存储，数据库只保存对象地址及元数据；是否使用 `bytea` 应根据备份、事务和访问模式评估。

[字符类型参考 ↪](https://www.postgresql.org/docs/18/datatype-character.html)
[二进制类型参考 ↪](https://www.postgresql.org/docs/18/datatype-binary.html)

# 日期与时间

## 常用类型

| 类型 | 含义 | 常见用途 |
| :--- | :--- | :--- |
| `date` | 日期，不含时间 | 生日、账期、节假日 |
| `time` | 一天中的时间，不含日期和时区 | 营业时间、每日提醒时间 |
| `timestamp` | 日期和时间，不含时区 | 本地日程中的“墙上时间” |
| `timestamptz` | 日期和时间，带时区语义 | 创建时间、事件发生时间、跨地区系统 |
| `interval` | 时间间隔 | “持续 30 分钟”“延后 2 天” |

`timestamp` 是 `timestamp without time zone` 的简写；`timestamptz` 是 `timestamp with time zone` 的 PostgreSQL 简写。时间精度可以写成 `timestamp(3)`，表示保留毫秒级小数，允许的精度范围为 0 到 6。

## timestamp 与 timestamptz 的区别

`timestamptz` 保存的是一个明确的时间点：输入的时区偏移会被换算，内部按 UTC 保存，输出时再按照当前会话时区显示。它不会保留原始输入时区名称。

```postgresql
SET TIME ZONE 'Asia/Shanghai';

SELECT TIMESTAMPTZ '2026-08-28 09:00:00+08' AS shanghai_time;

SET TIME ZONE 'UTC';

SELECT TIMESTAMPTZ '2026-08-28 09:00:00+08' AS utc_time;
```

同一个 `timestamptz` 值在不同会话时区中显示的钟表时间可能不同，但表示的是同一个瞬间。要将它转换为指定时区的本地时间，可以使用 `AT TIME ZONE`：

```postgresql
SELECT occurred_at AT TIME ZONE 'Asia/Shanghai'
FROM events;
```

`timestamp` 不表示一个全球统一的时间点。它只是保存日期和钟表时间，输入中的时区偏移不会参与换算：

```postgresql
SELECT TIMESTAMP '2026-08-28 09:00:00+08';
-- 时区偏移会被忽略
```

需要记录“发生在什么时候”的事件时，通常选 `timestamptz`；需要记录“每天几点开始营业”这类不绑定时区的规则时，选 `time` 或 `timestamp`。

## 日期时间输入与当前时间

建议使用不含歧义的 ISO 8601 格式，并给需要时区语义的字面量显式写出类型：

```postgresql
SELECT DATE '2026-08-28';
SELECT TIMESTAMP '2026-08-28 09:00:00';
SELECT TIMESTAMPTZ '2026-08-28 09:00:00+08';
SELECT INTERVAL '2 days 3 hours';
```

`CURRENT_TIMESTAMP`、`CURRENT_DATE` 等 SQL 函数返回当前事务开始时的时间；`clock_timestamp()` 返回读取时的实际系统时间。在同一个长事务中，两者的行为不同：

```postgresql
SELECT CURRENT_TIMESTAMP, clock_timestamp();
```

> 不要在持久化定义、预编译语句或需要长期复用的表达式中把 `'now'`、`'tomorrow'` 这类文本当作动态当前时间；应使用 `CURRENT_TIMESTAMP`、`CURRENT_DATE` 等函数。

`time with time zone`（别名 `timetz`）虽然存在，但使用场景较少；大多数应用使用 `date`、`time`、`timestamp` 和 `timestamptz` 的组合即可。

[日期与时间类型参考 ↪](https://www.postgresql.org/docs/18/datatype-datetime.html)

# 布尔值与 NULL

## boolean

`boolean` 只有三个状态：`TRUE`、`FALSE` 和 `NULL`。其中 `NULL` 表示“未知或缺失”，不是 `FALSE`，也不是空字符串或数字 0。

推荐使用清晰的布尔字面量和条件：

```postgresql
CREATE TABLE feature_flags (
    feature_name text PRIMARY KEY,
    enabled boolean NOT NULL DEFAULT false
);

SELECT *
FROM feature_flags
WHERE enabled IS TRUE;
```

判断空值必须使用 `IS NULL` 或 `IS NOT NULL`，不能写成 `= NULL`：

```postgresql
SELECT *
FROM users
WHERE deleted_at IS NULL;

SELECT COALESCE(display_name, '未设置') AS display_name
FROM users;
```

`COALESCE` 返回从左到右第一个非空值，但传入的参数需要能转换为兼容的类型。

# UUID

`uuid` 是 128 位的通用唯一标识符。它适合分布式系统和不希望暴露连续数据库编号的场景；代价是占用空间比 `integer` 更大，索引和日志也可能更宽。

PostgreSQL 18 原生提供 UUID v4 和 UUID v7 的生成函数：

```postgresql
SELECT gen_random_uuid();  -- UUID v4
SELECT uuidv4();           -- UUID v4
SELECT uuidv7();           -- 按时间排序特征生成的 UUID v7
```

新表可以直接把 UUID 设为默认值：

```postgresql
CREATE TABLE request_log (
    id         uuid PRIMARY KEY DEFAULT uuidv7(),
    created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    payload    jsonb NOT NULL DEFAULT '{}'::jsonb
);
```

UUID v7 带有时间排序特征，在部分按时间写入的索引场景中可以减少随机写入；是否使用它仍要结合数据分布、隐私要求和客户端兼容性评估。UUID 本身不等于安全令牌，不要把它当作权限控制。

[UUID 类型参考 ↪](https://www.postgresql.org/docs/18/datatype-uuid.html)
[UUID 函数参考 ↪](https://www.postgresql.org/docs/18/functions-uuid.html)

# JSON 与 JSONB

## 两种 JSON 类型

PostgreSQL 提供 `json` 和 `jsonb`：

| 类型 | 存储方式 | 特点 |
| :--- | :--- | :--- |
| `json` | 保存输入文本 | 保留空白、键顺序和重复键，读取时需要重新解析 |
| `jsonb` | 分解后的二进制格式 | 写入时有转换开销，但查询更快，支持常用索引 |

大多数需要查询、过滤或更新 JSON 属性的应用应优先使用 `jsonb`。如果必须保留原始文本格式、空白或键顺序，再考虑 `json`。对于结构稳定、需要强约束和频繁关联查询的字段，仍应设计为普通列，而不是全部塞进 JSON。

## 基本操作

```postgresql
CREATE TABLE profiles (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    attributes jsonb NOT NULL DEFAULT '{}'::jsonb
);

INSERT INTO profiles (attributes)
VALUES ('{"plan": "pro", "notifications": {"email": true}}');

-- -> 返回 jsonb，->> 返回 text
SELECT attributes -> 'notifications' ->> 'email' AS email_enabled
FROM profiles;

SELECT *
FROM profiles
WHERE attributes @> '{"plan": "pro"}'::jsonb;
```

常用运算符：

- `->`：按键或数组下标取出 JSON 值，结果仍是 JSON。
- `->>`：取出 JSON 值并转换为文本。
- `#>`、`#>>`：按路径取值，分别返回 JSON 或文本。
- `@>`：判断左侧 `jsonb` 是否包含右侧结构。
- `?`：判断顶层键或数组元素是否存在。

取不存在的键通常返回 `NULL`，不会自动报错；需要把“缺失”和 JSON 中明确的 `null` 区分开时，应使用相应的存在性判断和 JSON 函数。

`jsonb` 可以建立 GIN 索引：

```postgresql
CREATE INDEX profiles_attributes_gin_idx
    ON profiles USING GIN (attributes);
```

JSON 文档仍应保持相对稳定的结构。一个 JSON 字段的更新会锁住所在行；把频繁变化、需要独立更新的内容全部放进一个超大 JSON 文档，可能增加锁竞争和查询复杂度。

[JSON 类型参考 ↪](https://www.postgresql.org/docs/18/datatype-json.html)

# 数组

PostgreSQL 支持任意基础类型、枚举、复合类型、范围类型和域类型的数组。数组下标从 1 开始，而不是从 0 开始：

```postgresql
CREATE TABLE articles (
    id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tags text[] NOT NULL DEFAULT ARRAY[]::text[]
);

INSERT INTO articles (tags)
VALUES (ARRAY['postgresql', 'database']);

SELECT tags[1], cardinality(tags)
FROM articles
WHERE 'database' = ANY(tags);

SELECT unnest(tags)
FROM articles;
```

也可以使用数组字面量：

```postgresql
SELECT '{red,green,blue}'::text[];
SELECT ARRAY[1, 2, 3]::integer[];
```

注意事项：

- `integer[3]`、`integer[3][3]` 中写出的长度和维度在 PostgreSQL 当前实现中不会作为运行时限制；如果需要固定长度，应额外使用 `CHECK`。
- `ANY(array)` 可以判断某个值是否出现在数组中，`unnest` 可以将数组展开为多行。
- 数组适合少量、原子性的集合，例如标签或坐标；需要单独增删、关联、去重和统计时，优先使用子表。
- 查询数组包含关系时可以考虑 GIN 索引，但应根据实际查询和数据量验证收益。

```postgresql
CREATE INDEX articles_tags_gin_idx
    ON articles USING GIN (tags);
```

[数组参考 ↪](https://www.postgresql.org/docs/18/arrays.html)

# 枚举、域与范围类型

## 枚举类型 enum

枚举是一个静态、有顺序的值集合。适合状态数量少且变化很少的场景：

```postgresql
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'cancelled');

CREATE TABLE orders (
    id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status order_status NOT NULL DEFAULT 'pending'
);

INSERT INTO orders (status) VALUES ('paid');
```

枚举值按声明顺序比较，标签区分大小写。现有枚举可以增加或重命名值，但不能直接删除值或改变已有值的顺序。状态经常变化、需要多语言名称或需要附加属性时，使用字典表通常比 enum 更易维护。

## 域类型 domain

域类型是在基础类型上增加一组可复用约束。例如：

```postgresql
CREATE DOMAIN positive_amount AS numeric(12, 2)
CHECK (VALUE >= 0);

CREATE TABLE refunds (
    id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    amount positive_amount NOT NULL
);
```

域约束可以集中维护，多个表复用同一规则。域上的 `CHECK` 对 `NULL` 通常会得到 UNKNOWN，而 UNKNOWN 会通过检查；如果某列不允许空值，仍应在列上声明 `NOT NULL`。

[域类型参考 ↪](https://www.postgresql.org/docs/18/domains.html)

## 范围类型 range

范围类型把一段连续值作为一个值保存，常用于预约时间、有效期和价格区间。内置类型包括：

- `int4range`、`int8range`：整数范围
- `numrange`：数值范围
- `tsrange`、`tstzrange`：不带时区或带时区的时间戳范围
- `daterange`：日期范围
- 对应的 multirange 类型：保存多个不连续范围

推荐用半开区间 `[)` 表示“包含开始，不包含结束”，这样相邻区间不会重复计算：

```postgresql
CREATE TABLE room_bookings (
    id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id integer NOT NULL,
    during tstzrange NOT NULL
);

INSERT INTO room_bookings (room_id, during)
VALUES (
    101,
    tstzrange(
        TIMESTAMPTZ '2026-08-28 09:00:00+08',
        TIMESTAMPTZ '2026-08-28 10:00:00+08',
        '[)'
    )
);

SELECT *
FROM room_bookings
WHERE during && tstzrange(
    TIMESTAMPTZ '2026-08-28 09:30:00+08',
    TIMESTAMPTZ '2026-08-28 10:30:00+08',
    '[)'
);
```

`&&` 判断范围是否重叠，`@>` 判断范围是否包含某个元素或范围。对范围列可以建立 GiST 索引；如果要约束同一房间的预约不能重叠，可以进一步学习排他约束和 `btree_gist` 扩展。

[枚举类型参考 ↪](https://www.postgresql.org/docs/18/datatype-enum.html)
[范围类型参考 ↪](https://www.postgresql.org/docs/18/rangetypes.html)

# 网络地址、全文检索与其他类型

## 网络地址

`inet` 用于 IPv4/IPv6 主机地址或带掩码的地址，`cidr` 用于网络段，`macaddr` 和 `macaddr8` 用于 MAC 地址。相比用 `text` 保存 IP，它们能在输入时校验格式，并提供专用运算符：

```postgresql
CREATE TABLE access_logs (
    client_ip inet NOT NULL
);

SELECT *
FROM access_logs
WHERE client_ip <<= inet '10.0.0.0/8';
```

`inet` 可以表示单个主机，也可以带网络掩码；`cidr` 要求输入是规范的网络地址。需要按网段查询时，优先使用这些类型。

[网络地址类型参考 ↪](https://www.postgresql.org/docs/18/datatype-net-types.html)

## 全文检索类型

`tsvector` 表示经过处理、适合检索的文档，`tsquery` 表示检索条件。它们通常配合 `to_tsvector`、`plainto_tsquery` 和 `@@` 使用：

```postgresql
SELECT to_tsvector('english', 'PostgreSQL supports full text search')
       @@ plainto_tsquery('english', 'full text');
```

中文全文检索需要选择合适的分词和词典方案；仅把中文文本转换成 `tsvector` 并不等于获得理想的中文搜索效果。

[全文检索类型参考 ↪](https://www.postgresql.org/docs/18/datatype-textsearch.html)

## bit、xml 与几何类型

- `bit(n)`：固定长度位串，适合位掩码等场景；`bit varying(n)` 是可变长度位串。
- `xml`：保存 XML 数据，只有在系统确实使用 XML 时才选择。
- `point`、`line`、`box`、`polygon`、`circle` 等几何类型用于平面几何；地理信息系统通常使用 PostGIS，而不是直接依赖这些基础类型。

# 类型转换

PostgreSQL 会在表达式中尝试进行隐式类型转换，但隐式转换可能影响运算结果或导致操作符无法匹配。需要明确意图时，使用显式转换。

常见写法有两种：

```postgresql
SELECT '42'::integer;
SELECT CAST('2026-08-28' AS date);
SELECT 10::numeric / 3;
```

整数除法会丢弃小数部分：

```postgresql
SELECT 10 / 3;           -- 结果为 3
SELECT 10::numeric / 3;  -- 结果为带小数的 numeric 值，例如 3.3333333333333333
```

从文本转换为日期、数字或 UUID 时，输入必须符合目标类型的格式，否则会出现 `invalid input syntax`。应用程序应使用带类型的参数绑定，不要通过字符串拼接 SQL 来“模拟类型转换”。

[类型转换参考 ↪](https://www.postgresql.org/docs/18/typeconv.html)

# 综合示例：一张合理的业务表

下面的示例把本章常见选择组合在一起：

```postgresql
CREATE TABLE products (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku          text NOT NULL UNIQUE,
    price        numeric(12, 2) NOT NULL CHECK (price >= 0),
    available_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    tags         text[] NOT NULL DEFAULT ARRAY[]::text[],
    metadata     jsonb NOT NULL DEFAULT '{}'::jsonb,
    is_active    boolean NOT NULL DEFAULT true
);
```

这个设计的含义是：

- `id` 是数据库内部的自增技术主键。
- `sku` 是需要唯一约束的业务编码。
- `price` 使用精确小数并限制为非负。
- `available_at` 表示明确的时间点。
- `tags` 保存少量标签；如果标签需要独立管理，应拆成关联表。
- `metadata` 保存不稳定但需要查询的扩展属性。
- `is_active` 使用非空布尔值，并设置默认状态。

# 常见问题

## 为什么金额不使用 real 或 double precision？

浮点数以二进制近似值保存，某些十进制小数无法精确表示，连续计算后可能出现舍入误差。金额、税率和账务结果应使用 `numeric(p,s)`，并根据业务规则设置 `CHECK`。

## 为什么自增编号不连续？

序列取值与事务提交不是同一个机制。回滚、并发插入、批量操作或缓存都可能造成间隙。只要编号唯一，间隙通常是正常现象；如果业务要求连续编号，应单独设计受控的编号流程。

## 为什么保存了带时区的值，查询显示却不同？

`timestamptz` 输出会按照当前会话时区显示。先执行以下命令确认会话时区，再用 `AT TIME ZONE` 按需求展示：

```postgresql
SHOW TIME ZONE;
SELECT occurred_at AT TIME ZONE 'Asia/Shanghai'
FROM events;
```

## 为什么 `= NULL` 查不到结果？

`NULL` 表示未知，任何与 `NULL` 的普通比较结果都不是 `TRUE`。请使用 `IS NULL`、`IS NOT NULL`，或在需要默认值时使用 `COALESCE`。

## 为什么 JSON 查询不到字段？

先确认列是 `jsonb` 还是 `json`，再确认使用 `->` 还是 `->>`。前者返回 JSON，后者返回文本；路径或键名拼写错误时，取值通常返回 `NULL`。需要判断键是否存在时使用 `?` 或 JSON 函数。

## 为什么数组下标不是从 0 开始？

PostgreSQL 数组默认从 1 开始。应用代码和 SQL 之间传递数组下标时，要明确转换规则，避免出现偏移一位的问题。

## 为什么 varchar(255) 不是通用的数据校验？

`varchar(255)` 只限制字符长度，不能验证邮箱、手机号、业务编码或其他格式。格式规则应使用合适的 `CHECK`、专用类型或应用层校验，必要时再配合索引和唯一约束。

# 选型检查清单

- 先写清字段的业务含义，再选择存储类型。
- 整数默认考虑 `integer`；大型编号和计数器考虑 `bigint`。
- 金额和精确小数使用 `numeric`，不要使用浮点数代替。
- 新表的自增主键优先使用身份列；不要把序列当成连续业务编号。
- 普通文本优先使用 `text`；长度上限和格式规则分别用约束表达。
- 记录事件发生时间通常使用 `timestamptz`，并统一约定会话时区。
- `NULL`、`FALSE`、空字符串和数字 0 是不同概念。
- 需要查询和索引的 JSON 属性使用 `jsonb`，稳定字段保留为普通列。
- 数组只用于小量、原子性的集合；需要关系操作时使用关联表。
- 对跨系统输入、边界值和隐式转换保持警惕，必要时显式写出类型。
