# 用户管理

[角色属性参考 ↪](https://www.postgresql.org/docs/18/role-attributes.html)

在 PostgreSQL 中，**角色（role）**是可以拥有数据库对象、拥有权限或成为其他角色成员的身份。角色在整个数据库集群中有效，而不是只存在于某一个数据库中。

“用户（user）”和“组（group）”不是两种独立的对象，而是角色的两种常见用法：

- 具有 `LOGIN` 属性的角色可以作为客户端登录用户。
- 通常不允许登录（`NOLOGIN`）的角色可以作为权限组，统一向成员授予权限。
- `CREATE USER` 是 `CREATE ROLE` 的便捷写法，区别是 `CREATE USER` 默认带有 `LOGIN` 属性；`CREATE ROLE` 默认不允许登录。

数据库角色与 macOS/Linux 的操作系统用户相互独立。两者可以使用相同的名称，但一个操作系统用户并不会自动获得同名数据库角色的权限。

```text
角色（role）
├── 登录角色：app_user LOGIN
└── 权限组：app_readonly NOLOGIN
              └── app_user 是其成员
```

> 角色名通常使用小写字母、数字和下划线。未加双引号的标识符会自动折叠为小写；
>
> 除非确有必要，不要创建需要写成 `"AppUser"` 的大小写敏感角色名。

# 角色属性

角色属性决定“这个角色能不能做某类管理操作”，但不等同于表上的 `SELECT`、`INSERT` 等对象权限。常用属性如下：

| 属性 | 作用 | 建议 |
| :--- | :--- | :--- |
| `LOGIN` / `NOLOGIN` | 是否允许作为初始登录角色 | 应用用户使用 `LOGIN`，权限组使用 `NOLOGIN` |
| `SUPERUSER` / `NOSUPERUSER` | 是否绕过大多数权限检查 | 业务账号使用 `NOSUPERUSER` |
| `CREATEDB` / `NOCREATEDB` | 是否可以创建数据库 | 只授予确实需要创建数据库的管理员 |
| `CREATEROLE` / `NOCREATEROLE` | 是否可以创建、修改或删除其他角色 | 只授予受信任的角色管理员 |
| `INHERIT` / `NOINHERIT` | 是否自动继承所属角色的对象权限 | 普通登录角色通常保留 `INHERIT` |
| `REPLICATION` / `NOREPLICATION` | 是否可以进行复制连接或管理复制槽 | 仅授予复制专用账号 |
| `BYPASSRLS` / `NOBYPASSRLS` | 是否绕过行级安全策略（RLS） | 除非明确需要，否则使用 `NOBYPASSRLS` |
| `CONNECTION LIMIT` | 限制该角色的并发连接数，`-1` 表示不限制 | 应用账号可按连接池大小设置 |
| `VALID UNTIL` | 设置密码的失效时间 | 用于临时账号或定期轮换密码 |

超级用户可以绕过权限检查，但不能绕过“登录认证”本身。超级用户权限范围很大，误操作可能导致数据泄露、删除或配置损坏，因此日常操作应尽量使用普通角色。

> `CREATEDB`、`CREATEROLE` 等管理属性不会因为普通的角色成员关系自动继承。需要临时使用某个角色的管理能力时，应明确使用 `SET ROLE`，并限制成员关系的授予范围。

[角色属性参考 ↪](https://www.postgresql.org/docs/18/role-attributes.html)

# 角色与权限的三层关系

管理 PostgreSQL 权限时，可以按以下顺序思考：

1. 角色属性：例如 `LOGIN`、`CREATEDB` 和 `SUPERUSER`。
2. 角色成员关系：例如把 `app_readonly` 授予 `alice`，让 Alice 继承这个权限组的对象权限。
3. 对象权限：例如对 `app.orders` 授予 `SELECT`，对数据库授予 `CONNECT`，对模式授予 `USAGE`。

只创建登录角色并不能让它访问任何业务表。一个通过 TCP 登录的应用用户，通常至少需要数据库的 `CONNECT` 权限、模式的 `USAGE` 权限，以及表或序列上的具体权限。

## 临时切换角色

如果当前登录角色是某个权限组的成员，可以在会话中临时切换到该组，再恢复原来的角色：

```postgresql
SET ROLE app_readonly;
SELECT current_user;  -- 当前生效角色为 app_readonly
RESET ROLE;
SELECT current_user;  -- 恢复为最初登录的角色
```

`SET ROLE` 只影响当前会话，不会修改角色成员关系；是否允许切换还取决于角色成员关系的管理选项。生产环境应明确授予必要的成员关系，避免把高权限角色随意授予登录用户。

PostgreSQL 16 及更高版本可以为每一条角色成员关系单独设置以下选项：

| 成员关系选项 | 作用 |
| :--- | :--- |
| `INHERIT` | 是否自动使用被授予角色的对象权限 |
| `SET` | 是否允许成员通过 `SET ROLE` 切换到被授予角色 |
| `ADMIN` | 是否允许成员继续向其他角色授予或撤销该成员关系 |

普通应用账号通常只需要继承读写权限，不需要 `ADMIN`；只有确实需要委派角色管理工作的账号才应获得 `ADMIN`。

# 创建角色

## 使用 SQL 创建

推荐先创建不带密码的角色，再使用 `psql` 的 `\password` 命令交互式设置密码，避免明文密码出现在 Shell 历史记录中：

```postgresql
-- 登录用户：允许连接，但不授予超级用户或建库权限
CREATE ROLE app_user LOGIN;

-- 权限组：不能直接登录，只用于集中管理权限
CREATE ROLE app_readonly NOLOGIN;
CREATE ROLE app_writer NOLOGIN;

-- 将权限组授予登录用户
GRANT app_readonly TO app_user;

-- 在 psql 中安全地设置密码，随后按提示输入两次
\password app_user
```

也可以使用 `CREATE USER` 创建登录角色：

```postgresql
CREATE USER report_user;
```

`CREATE USER` 只是 `CREATE ROLE ... LOGIN` 的别名。实际项目中建议显式写出角色用途，并避免使用 `SUPERUSER`：

```postgresql
CREATE ROLE report_user LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
```

创建超级用户只应由现有超级用户执行，学习示例不建议这样做：

```postgresql
-- 不推荐用于业务账号
CREATE ROLE db_admin LOGIN SUPERUSER;
```

## 使用命令行创建

`createuser` 和 `dropuser` 是 SQL 命令的命令行封装。创建登录角色时可以使用 `--login`，并用 `--pwprompt` 交互式输入密码：

```shell
createuser --login --pwprompt app_user
```

如果只想创建权限组：

```shell
createuser --no-login app_readonly
```

执行这些命令的操作系统用户，必须能以有权创建角色的数据库角色连接到服务器；必要时使用 `-U`、`-h` 和 `-d` 指定连接参数，而不是直接使用操作系统的 `root` 身份。

# 查看角色

## 使用 psql 元命令

```postgresql
\du
\du+
\drg
```

`\du` 查看角色属性，`\du+` 查看更详细的信息，`\drg` 查看角色成员关系。元命令属于 `psql` 客户端，不是标准 SQL，不需要分号。

## 查询系统视图

`pg_roles` 会隐藏密码字段，适合用于查看角色属性：

```postgresql
SELECT
    rolname,
    rolcanlogin,
    rolsuper,
    rolcreatedb,
    rolcreaterole,
    rolinherit,
    rolreplication,
    rolbypassrls,
    rolconnlimit,
    rolvaliduntil
FROM pg_roles
ORDER BY rolname;
```

查看当前会话使用的身份：

```postgresql
SELECT
    session_user,       -- 最初登录的角色
    current_user,       -- 当前生效的角色，SET ROLE 后可能变化
    current_database();
```

查看某个角色是否可以登录或创建数据库：

```postgresql
SELECT
    rolname,
    rolcanlogin,
    rolcreatedb,
    rolcreaterole
FROM pg_roles
WHERE rolname = 'app_user';
```

# 修改角色

`ALTER ROLE` 可以修改角色属性；未写出的属性保持不变。

```postgresql
-- 禁止登录，用于临时停用账号
ALTER ROLE app_user NOLOGIN;

-- 恢复登录
ALTER ROLE app_user LOGIN;

-- 限制连接数
ALTER ROLE app_user CONNECTION LIMIT 10;

-- 设置密码失效时间（只针对密码认证）
ALTER ROLE app_user VALID UNTIL '2027-12-31 23:59:59+00';
```

修改密码时，优先使用 `psql` 的 `\password`：

```postgresql
\password app_user
```

也可以使用 SQL，但密码会出现在命令历史或日志中的风险更高：

```postgresql
ALTER ROLE app_user PASSWORD '请替换为强密码';
```

PostgreSQL 18 默认使用 `scram-sha-256` 保存新密码。可以查看当前设置：

```postgresql
SHOW password_encryption;
```

`md5` 密码认证已经被弃用，未来版本会移除。新部署应使用 SCRAM；如果从旧系统迁移，应确认所有客户端库支持 SCRAM 后，再为用户重新设置密码并调整 `pg_hba.conf`。

[密码认证参考 ↪](https://www.postgresql.org/docs/18/auth-password.html)

# 授予与撤销权限

## 常用对象权限

权限需要授予具体对象。常见对象和权限如下：

| 对象 | 常见权限 | 说明 |
| :--- | :--- | :--- |
| 数据库 | `CONNECT`、`CREATE`、`TEMPORARY` | 是否能连接、创建模式或创建临时表 |
| 模式 | `USAGE`、`CREATE` | 是否能访问模式中的对象、是否能在模式中创建对象 |
| 表/视图 | `SELECT`、`INSERT`、`UPDATE`、`DELETE`、`TRUNCATE`、`REFERENCES`、`TRIGGER`、`MAINTAIN` | 数据读写、约束、触发器和维护操作相关能力 |
| 序列 | `USAGE`、`SELECT`、`UPDATE` | 使用或读取自增序列时经常需要 |
| 函数/过程 | `EXECUTE` | 是否可以调用函数或过程 |

`ALL PRIVILEGES` 会一次授予当前对象上该角色可授予的全部权限，不代表超级用户，也不应在不了解影响时使用。

对象所有者通常天然拥有该对象的管理权限，即使从权限列表中撤销了某些权限，也不能用 `REVOKE` 把所有者变成普通读写用户。需要限制对象管理能力时，应由专门的所有者角色创建对象，再把业务权限授予应用角色。

## 最小权限示例

下面示例创建一个只读组和一个只读登录用户。对象权限应在目标数据库中执行：

```postgresql
-- 在管理员会话中执行
CREATE ROLE app_readonly NOLOGIN;
CREATE ROLE report_user LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
GRANT app_readonly TO report_user;

-- 连接到目标数据库后执行
GRANT CONNECT ON DATABASE learn_db TO app_readonly;
GRANT USAGE ON SCHEMA app TO app_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO app_readonly;
```

如果应用需要写入数据，可以创建单独的写入组，而不是给应用用户超级用户权限：

```postgresql
CREATE ROLE app_writer NOLOGIN;
GRANT app_writer TO app_user;

GRANT CONNECT ON DATABASE learn_db TO app_writer;
GRANT USAGE ON SCHEMA app TO app_writer;
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA app TO app_writer;
GRANT USAGE, SELECT, UPDATE
ON ALL SEQUENCES IN SCHEMA app TO app_writer;
```

> `GRANT` 不会自动授予下一级对象的权限。例如，只有模式 `USAGE` 仍然不能读取表；只有表权限而没有模式 `USAGE` 也无法通过该模式访问表。

## 撤销权限

使用 `REVOKE` 撤销已经授予的权限。撤销组权限时，成员将不再通过该组继承对应权限：

```postgresql
REVOKE UPDATE, DELETE ON ALL TABLES IN SCHEMA app FROM app_writer;
REVOKE app_readonly FROM report_user;
```

`PUBLIC` 表示所有角色。不要随意向 `PUBLIC` 授予写权限；发现不必要的默认权限时，可以明确撤销：

```postgresql
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
```

撤销权限只影响权限授予，不会删除表或数据。删除数据对象需要使用 `DROP`，应单独评估风险。

[GRANT 参考 ↪](https://www.postgresql.org/docs/18/sql-grant.html) · [REVOKE 参考 ↪](https://www.postgresql.org/docs/18/sql-revoke.html)

# 默认权限

`GRANT ... ON ALL TABLES IN SCHEMA ...` 只影响已经存在的表。为了让将来由某个所有者创建的新表也自动获得权限，需要使用 `ALTER DEFAULT PRIVILEGES`：

```postgresql
-- 以 app_owner 身份创建的未来表，自动授予只读组 SELECT
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app
GRANT SELECT ON TABLES TO app_readonly;

-- 如果新表使用自增序列，还需要为未来序列授予权限
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app
GRANT USAGE, SELECT ON SEQUENCES TO app_writer;
```

注意以下几点：

- 默认权限只对指定所有者将来创建的对象生效，不会追溯修改已有对象。
- `FOR ROLE app_owner` 指定的是对象所有者，不是“执行命令后切换成的用户”。
- 执行者必须是对象所有者、超级用户或拥有相应管理权限的角色。
- 如果有多个对象所有者，需要分别为每个所有者设置默认权限。

# 预定义角色

[预定义角色参考 ↪](https://www.postgresql.org/docs/18/predefined-roles.html)

PostgreSQL 提供了一些预定义角色，用于授予常见的监控或数据访问能力。例如：

```postgresql
-- 允许监控账号读取常见的统计信息
GRANT pg_monitor TO monitor_user;

-- 允许分析账号读取所有表、视图和序列的数据
GRANT pg_read_all_data TO analyst_user;

-- 允许写入所有表、视图和序列，谨慎授予
GRANT pg_write_all_data TO data_loader;
```

`pg_read_all_data` 和 `pg_write_all_data` 不会绕过行级安全策略（RLS）。`pg_read_server_files`、`pg_write_server_files` 和 `pg_execute_server_program` 可以访问数据库服务器上的文件或执行程序，权限非常敏感，不应作为普通数据读写权限使用。

# 删除角色

## 没有对象和权限依赖时

```postgresql
DROP ROLE IF EXISTS report_user;
```

`DROP USER` 是 `DROP ROLE` 的别名。删除角色不会删除其他成员角色，但会自动撤销相关角色成员关系。

## 角色拥有对象时

角色可能拥有表、序列、函数、数据库或表空间，也可能持有其他对象上的权限。直接 `DROP ROLE` 通常会失败。更稳妥的流程是：

1. 先决定对象应该转移给哪个新的所有者。
2. 在**每个包含该角色对象的数据库**中执行 `REASSIGN OWNED` 和 `DROP OWNED`。
3. 处理该角色拥有的数据库或表空间。
4. 最后执行 `DROP ROLE`。

```postgresql
-- 在每个相关数据库中执行
REASSIGN OWNED BY old_user TO app_owner;
DROP OWNED BY old_user;

-- 如果 old_user 仍拥有数据库，先转移数据库所有权
ALTER DATABASE learn_db OWNER TO app_owner;

-- 所有数据库中的依赖都处理完后，再删除角色
DROP ROLE old_user;
```

`REASSIGN OWNED` 只转移所有权，不会撤销 old_user 在其他对象上的权限，所以通常要按顺序同时执行 `DROP OWNED`。`DROP OWNED` 会删除当前数据库中由该角色拥有的剩余对象，并撤销它获得的权限；如果不确定对象是否应该删除，不要直接添加 `CASCADE`。

执行 `REASSIGN OWNED` 时，当前角色需要具备对旧角色和新所有者角色的相应成员资格；超级用户可以执行完整的迁移操作。

[删除角色参考 ↪](https://www.postgresql.org/docs/18/role-removal.html) · [REASSIGN OWNED 参考 ↪](https://www.postgresql.org/docs/18/sql-reassign-owned.html)

# 启用密码认证

## 查看认证配置文件

`pg_hba.conf`（Host-Based Authentication）决定客户端如何认证。先在 `psql` 中查看当前实例实际使用的文件位置：

```postgresql
SHOW hba_file;
```

配置文件中的规则按从上到下的顺序匹配，**第一条匹配的规则会生效**。常见字段如下：

```text
连接类型    数据库    用户       客户端地址       认证方法
local       all       all                         scram-sha-256
host        learn_db  app_user   127.0.0.1/32     scram-sha-256
```

- `local` 匹配 Unix socket 连接，不填写客户端 IP。
- `host` 匹配 TCP/IP 连接，需要填写客户端地址或 CIDR 网段。
- `all` 是通配符，表示所有数据库或所有角色。
- `scram-sha-256` 是 PostgreSQL 18 新部署推荐的密码认证方式。

## 本地开发示例

编辑 `SHOW hba_file;` 输出的文件，在已有规则前加入精确规则。例如只允许本机的 `app_user` 通过 TCP 连接 `learn_db`：

```text
# 本机 IPv4：只允许 app_user 连接 learn_db
host    learn_db    app_user    127.0.0.1/32    scram-sha-256

# 本机 IPv6：只允许 app_user 连接 learn_db
host    learn_db    app_user    ::1/128         scram-sha-256
```

如果希望所有本地 socket 连接都使用密码认证，可以配置：

```text
local   all         all                         scram-sha-256
```

修改后以管理员角色重新加载配置即可，不必为了 `pg_hba.conf` 重启整个服务器：

```postgresql
SELECT pg_reload_conf();
```

然后使用密码验证连接：

```shell
psql -h localhost -p 5432 -U app_user -d learn_db -W
```

连接成功后可以确认当前身份：

```postgresql
SELECT session_user, current_user, current_database();
```

## 远程连接注意事项

不要直接使用下面这种对所有地址开放的规则：

```text
# 不推荐：任意地址都可以尝试连接
host    all    all    0.0.0.0/0    scram-sha-256
```

如果确实需要远程访问，应将地址限制为实际客户端网段或单个 IP，并同时配置防火墙、强密码和 TLS；例如：

```text
# 示例：只允许 192.168.1.10 访问 learn_db
host    learn_db    app_user    192.168.1.10/32    scram-sha-256
```

认证方式 `trust` 不会验证密码，只适合明确隔离的临时本机学习环境，不应部署在可被其他用户或网络访问的服务器上。`md5` 已被弃用，新系统应迁移到 `scram-sha-256`。

[pg_hba.conf 参考 ↪](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html) · [密码认证参考 ↪](https://www.postgresql.org/docs/18/auth-password.html)

# 常见问题

## role "xxx" does not exist

数据库角色不存在，或连接时指定了错误的 `-U` 用户名。先执行 `\du` 检查角色，再使用正确的角色创建或连接。

## password authentication failed for user "xxx"

常见原因包括密码错误、角色没有设置密码、`pg_hba.conf` 的规则未匹配预期，或连接到了另一套 PostgreSQL 实例。依次检查 `SHOW hba_file;`、`SELECT version();`、角色的 `rolcanlogin` 和密码设置。

## permission denied for schema app

角色可能拥有表权限，但缺少模式的 `USAGE` 权限：

```postgresql
GRANT USAGE ON SCHEMA app TO app_readonly;
```

## permission denied for sequence ...

插入使用 `SERIAL` 或 `IDENTITY` 列时，除了表的 `INSERT` 权限，通常还需要序列权限：

```postgresql
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA app TO app_writer;
```

## must be owner of ...

很多 `ALTER`、`GRANT` 和 `DROP` 操作要求当前角色是对象所有者、超级用户，或拥有相应的管理权限。先检查对象所有者，再使用 `SET ROLE` 或让对象所有者执行操作，不要习惯性地把业务账号改成超级用户。

# 安全检查清单

- 应用账号使用 `NOSUPERUSER`、`NOCREATEDB` 和 `NOCREATEROLE`。
- 按“角色组 + 最小对象权限”设计权限，避免给单个应用账号授予 `ALL PRIVILEGES`。
- 新部署使用 `scram-sha-256`，不要新增 `md5` 或开放式 `trust` 规则。
- 远程访问只允许必要的 IP 或网段，不使用 `0.0.0.0/0` 作为默认规则。
- 使用 `\password` 设置密码，避免把真实密码写进 SQL 文件、Shell 历史或版本库。
- 删除角色前先确认对象所有权、默认权限和跨数据库依赖，必要时先备份。
- 定期检查 `\du+`、`\drg` 和对象权限，及时禁用不再使用的账号。
